지능을 쓰는 툴LLM을 호출하는 블로그 글쓰기 에이전트

앞선 두 트랙은 이미 만들어진 하네스를 실행했다. 이번엔 한 칸 안으로 들어간다 — LLM API를 툴 안에서 직접 호출해, 판단할 줄 아는 툴을 손으로 짠다. 실행하는 코드가 아니라 설계의 감각을 다룬다.

이 트랙으로 얻는 것

이 글은 돌려보는 실습이 아니라 읽고 이해하는 설계 가이드다. 다 읽으면 다음이 또렷해진다.

  • "지능을 쓰는 툴"이라는 발상 — 툴이 정해진 일만 하는 게 아니라, 그 안에서 LLM을 불러 판단·생성을 한다
  • 툴 안 프롬프트에 요구사항(무엇을)과 하네스(어떻게·제약)를 함께 실어 출력을 원하는 방향으로 제어하는 법
  • 생성을 한 방에 믿지 않고 LLM-as-Judge로 자기검증 → 수정하는 루프의 구조
  • 왜 이 구조가 "AI가 글을 뽑아준다"가 아니라 하네스 안에서 굴러가는 에이전트인지

전제. 이 트랙은 코드를 실행하지 않는다. 등장하는 프롬프트·의사코드는 모두 개념을 보여주기 위한 예시다 — 그대로 붙여 돌리는 용도가 아니다. 전용 템플릿 레포는 준비 중이다.

핵심 — 툴이 지능을 쓴다

보통의 툴은 정해진 일만 한다. fetch_url(url)은 페이지를 가져오고, save_file(path)는 파일을 쓴다 — 입력이 같으면 출력도 같다. 결정적이다.

그런데 툴 안에서 LLM API를 호출하면 성질이 달라진다. 그 툴은 이제 판단하고 생성하는 툴이 된다 — "이 자료로 도입부를 써라", "이 초안이 요구사항을 만족하는지 채점해라" 같은, 규칙으로 못 박을 수 없는 일을 한다.

일반 툴      입력 → [정해진 규칙]        → 출력   (결정적)
지능형 툴    입력 → [프롬프트로 LLM 호출] → 출력   (판단·생성)

여기서 핵심은 "프롬프트가 곧 제어"라는 점이다. 툴은 LLM에게 요구사항(무엇을 해라)만 던지지 않는다. 하네스(어떤 형식·톤·제약·금지)를 함께 실어 보낸다. 시리즈 3에서 말한 하네스 엔지니어링이 — 워크플로우 전체가 아니라 — 단 하나의 툴 호출 안에서도 똑같이 작동하는 것이다.

흐름 한눈에

이 트랙의 에이전트는 한 방에 글을 뽑지 않는다. 사람이 글을 쓰는 순서 그대로 — 모으고 · 쓰고 · 따져보고 · 고친다.

  [사용자 요구]  "주제 X로 블로그 글, 출처는 이 URL들"
        │
        ▼
  ┌───────────────┐   툴: 외부 URL/RSS를 실제로 가져온다
  │ 1. 출처 fetch │   (결정적 — LLM 호출 없음)
  └──────┬────────┘
         ▼
  ┌───────────────┐   지능형 툴: 요구사항 + 하네스 + 출처 →
  │ 2. 초안 작성  │   LLM이 글 초안 생성
  └──────┬────────┘
         ▼
  ┌───────────────┐   지능형 툴(LLM-as-Judge): 루브릭으로
  │ 3. 자기검증   │   초안을 채점 → 통과 / 수정지시
  └──────┬────────┘
         │  통과 ──────────────► 완성
         │  미달
         ▼
  ┌───────────────┐   지능형 툴: Judge의 지시를 받아
  │ 4. 수정       │   초안을 고쳐 다시 3으로
  └───────────────┘   (최대 N회 — 무한루프 방지)

1번만 결정적 툴이고, 2·3·4번이 모두 "지능을 쓰는 툴"이다. 같은 LLM이라도 어떤 프롬프트(=요구사항+하네스)를 받느냐에 따라 작가가 되기도, 심사위원이 되기도, 편집자가 되기도 한다.

1단계 — 출처 fetch (결정적 툴)

첫 단계는 지능이 필요 없다. 사용자가 준 URL·RSS를 그대로 가져오는 평범한 툴이다. 여기서 LLM을 부르지 않는 게 중요하다 — 출처는 사실이고, 사실은 생성하는 게 아니라 가져오는 것이다. (시리즈 1의 Blind Context: AI는 모르는 걸 그럴듯하게 지어낸다 — 그래서 근거는 코드로 못박는다.)

def fetch_sources(urls):
    # LLM 호출 없음. 실제 네트워크에서 본문만 긁어온다.
    return [ {"url": u, "text": download_main_text(u)} for u in urls ]

이렇게 가져온 출처 텍스트가 다음 단계 프롬프트에 근거로 실린다. 글은 모델의 기억이 아니라 이 출처에 기대게 만든다.

2단계 — 초안: 프롬프트 = 요구사항 + 하네스

이 트랙의 심장이다. 초안 툴은 LLM을 부르되, 요구사항과 하네스를 한 프롬프트에 함께 실어 보낸다. "글 써줘"가 아니라, 무엇을·어떻게·무엇은 하지 말 것까지 구조로 지시한다.

# 의사코드 — 툴 안에서 LLM을 부르는 모양 (실행용 아님)
def draft(topic, sources, audience):
    prompt = f"""
[요구사항]   ← 무엇을
- 주제: {topic}
- 독자: {audience}
- 출처(아래 본문)에 근거해서만 쓴다. 출처에 없는 사실은 쓰지 않는다.

[하네스]     ← 어떻게 · 제약
- 구조: 도입(질문) → 본문 3단락 → 결론(한 줄 요약)
- 분량: 800자 내외 / 톤: 단정한 한국어, 1인칭은 "우리"
- 금지: 과장 형용사, 출처 없는 단정, 메타 안내("이 글에서는...")
- 각 주장 끝에 [출처 번호]를 단다

[출처]
{format_sources(sources)}
"""
    return call_llm(model="claude-opus-4-8", prompt=prompt)

같은 모델, 같은 출처라도 [하네스] 블록을 바꾸면 결과의 방향이 바뀐다. 요구사항이 "무엇을"이라면, 하네스는 "어떻게 — 그리고 무엇은 절대 하지 말 것"이다. 제어는 여기서 일어난다.

3단계 — 자기검증: LLM-as-Judge

초안을 그대로 믿지 않는다. 같은 종류의 툴(LLM 호출)을 심사위원 역할로 한 번 더 쓴다. 작가에게 준 하네스를 이번엔 채점 루브릭으로 뒤집어 던진다 — "이 글이 그 제약을 지켰는가?"

# 의사코드 — 같은 LLM, 다른 프롬프트 → 심사위원이 된다
def judge(draft, topic, sources):
    prompt = f"""
너는 편집자다. 아래 초안을 루브릭으로 채점한다.

[루브릭] (각 항목 통과/미달 + 한 줄 근거)
1. 출처 근거: 모든 사실 주장이 출처에 있는가? 지어낸 곳은?
2. 구조: 도입→본문 3단락→결론을 지켰는가?
3. 톤·금지: 과장/메타 안내/출처 없는 단정이 없는가?
4. 주제 적합: 독자에게 실제로 답을 주는가?

[출력] 통과면 verdict="pass". 미달이면 verdict="revise"와
       고쳐야 할 곳을 '어디를 → 어떻게' 형태로 구체적으로.

[초안]
{draft}
[출처]
{format_sources(sources)}
"""
    return call_llm(model="claude-opus-4-8", prompt=prompt)  # 구조화 출력

여기서 시리즈 5의 명제가 그대로 산다 — 실행이 싸지면 판단이 비싸진다. 초안 생성(실행)은 한 번의 호출로 끝나지만, 그게 쓸 만한지 가르는 판단이 품질을 만든다. 그래서 작가와 심사위원을 분리한다. 자기가 쓴 걸 자기가 후하게 보는 편향을 끊기 위해, 채점은 별도의 호출로 한다.

4단계 — 수정 루프 (그리고 멈춤)

Judge가 revise를 내면, 그 구체적 지시를 들고 초안을 고치는 툴을 부른다. 고친 초안은 다시 3단계로 — 통과할 때까지. 단, 무한히 돌지 않는다. 횟수 상한을 둔다 (시리즈 4의 LOOPBACK 제한과 같은 발상).

# 의사코드 — 에이전트 루프 전체 (실행용 아님)
def write_post(topic, urls, audience, max_rounds=3):
    sources = fetch_sources(urls)          # 1. 결정적 툴
    text = draft(topic, sources, audience) # 2. 지능형 툴
    for _ in range(max_rounds):
        verdict = judge(text, topic, sources)   # 3. 지능형 툴(심사)
        if verdict.result == "pass":
            return text                          # 통과 → 완성
        text = revise(text, verdict.fixes, sources)  # 4. 지능형 툴(편집)
    return text  # 상한 도달 — 사람에게 넘긴다(게이트)

상한에 닿아도 그냥 토해내지 않는다 — 사람에게 넘기는 게이트가 된다. AI가 두 번 고쳐도 루브릭을 못 넘겼다면, 그건 모델이 아니라 요구사항이나 출처에 문제가 있다는 신호다. 판단의 책임은 사람에게 돌아온다.

정리 — 왜 이게 "하네스 안의 에이전트"인가

"주제 던지면 글 뽑아주는 AI"와 이 트랙의 차이는 한 줄로 압축된다.

생성을 구조 안에 가둔다. 출처는 코드로 못박고(fetch), 방향은 프롬프트의 하네스로 제어하고(draft), 결과는 별도의 심사로 검증하고(judge), 실패는 횟수 제한 안에서 복구하다 사람에게 넘긴다(loop·gate).

LLM API를 툴 안에서 쓴다는 건, 모델에게 자유를 주는 게 아니라 — 매 호출마다 요구사항과 하네스를 함께 쥐여 방향을 잡는 일이다. 그게 "지능을 쓰는 툴"이고, 그 툴들을 fetch → draft → judge → revise로 엮은 게 에이전트다.

다음. 이 흐름을 실제로 돌려볼 수 있는 전용 템플릿 레포는 준비 중이다. 공개되면 이 페이지에서 바로 연결한다 — 그때 직접 draft·judge 프롬프트를 바꿔가며 "하네스를 바꾸면 결과가 어떻게 휘는지"를 손으로 확인하게 된다.
